RDS TLS 설정을 양쪽에 맞추기

Terraform 담당(한민엽)과 Kubernetes·백엔드 담당(지인진)이 각각 준비할 내용을 정리했습니다. 현재 Terraform 코드 변경은 작업본에 반영됐지만, AWS에는 적용하지 않았습니다.

왜 이 설정을 추가하나요?

TLS는 애플리케이션과 데이터베이스 사이를 오가는 비밀번호와 SQL 통신을 암호화합니다. 인증서 검증을 함께 켜면 클라이언트가 접속한 서버가 실제 RDS인지와 RDS 주소가 인증서와 일치하는지도 확인합니다.

RDS에서 TLS를 강제하면 TLS 없는 연결은 거부됩니다. 따라서 RDS 쪽 강제 설정과 앱·초기화 Job의 TLS 연결 설정이 한 쌍으로 준비돼야 합니다.

순서 주의: RDS에서 TLS를 먼저 강제하면 TLS 설정이 아직 없는 앱이나 DB 초기화 Job은 접속이 끊깁니다. 클라이언트 설정을 먼저 준비하고 모두 확인한 뒤 실제 RDS에 적용합니다.

AWS는 MariaDB 11.4에서 require_secure_transport가 기본 OFF라고 설명합니다. 이 파라미터는 DB parameter group에서 ON으로 설정할 수 있고, 변경에 재부팅이 필요하지 않습니다. AWS 문서

담당별 작업

한민엽 · Terraform

  1. modules/data/main.tf의 MariaDB 11.4 DB parameter group에 TLS 강제 파라미터를 추가했습니다.
  2. 값은 require_secure_transport = ON, 적용 방식은 immediate입니다.
  3. terraform fmt -check와 git diff --check를 확인했습니다.
  4. 이 변경은 아직 AWS에 적용되지 않았습니다. 앱과 Job 준비가 확인된 뒤 apply 일정을 맞춥니다.

지인진 · Kubernetes와 백엔드

  1. DB 초기화 Job 컨테이너가 AWS RDS CA 번들을 읽을 수 있게 연결합니다.
  2. Job의 MariaDB 클라이언트에 TLS와 서버 인증서 검증 옵션을 전달합니다.
  3. 백엔드 JDBC 연결에 TLS 및 호스트 이름을 포함한 인증서 검증을 설정합니다.
  4. README에 CA 번들 준비, 마운트 경로, 설정 방법을 적습니다.
  5. 현재 MariaDB Connector/J 버전에서 사용하는 URL 옵션이 지원되는지 확인합니다.

Kubernetes 쪽 설정 예시

1. DB 초기화 Job

Job은 mariadb:11.4 클라이언트로 테이블을 만들고 앱 계정을 설정합니다. CA 번들은 비밀번호가 아니라 공개 인증서 자료이므로 Kubernetes Secret에 넣을 필요는 없습니다. 팀에서 정한 ConfigMap 또는 이미지 내 경로로 전달하고 컨테이너 안에서 읽을 수 있게 마운트합니다.

DB_CLIENT_OPTS="--ssl-ca=/certs/global-bundle.pem --ssl-verify-server-cert"

MariaDB CLI는 --ssl-ca로 신뢰할 CA 파일을 지정하고 --ssl-verify-server-cert로 서버 인증서를 확인합니다. MariaDB 클라이언트 문서

2. 백엔드 앱 DB 연결 (JPA가 사용하는 DataSource)

백엔드에서 JPA를 사용해도 DB와 실제로 통신하는 데는 JDBC 드라이버가 필요합니다. JPA는 객체와 테이블을 연결해 주는 계층이고, MariaDB Connector/J가 네트워크 연결을 담당합니다. 따라서 아래 spring.datasource.url은 JPA 대신 JDBC를 선택한다는 뜻이 아니라, JPA가 사용할 DB 연결과 TLS 옵션을 지정합니다.

기존 운영 예시의 URL은 RDS endpoint와 DB 이름을 사용합니다. 여기에 TLS 모드와 CA 번들 경로를 Connector/J 버전에 맞춰 추가해야 합니다. 개념적인 예시는 다음과 같습니다.

jdbc:mariadb://<RDS endpoint>:3306/sai?sslMode=verify-full&serverSslCert=/certs/global-bundle.pem

실제 옵션 이름과 CA 파일 지정 방식은 사용 중인 MariaDB Connector/J 버전 문서를 확인해 확정합니다. 운영 RDS의 DNS endpoint를 사용해야 서버 이름 검증이 가능합니다. IP 주소로 바꾸지 않습니다.

적용 순서

① 클라이언트 준비
Job과 백엔드가 CA 번들을 읽고 TLS 검증으로 연결하도록 코드와 설정을 준비합니다.
→
② 코드 확인
두 담당자가 경로, 옵션, RDS endpoint가 서로 맞는지 검토합니다. 로컬 kind 검증만으로 AWS 인증서 연결까지 확인했다고 간주하지 않습니다.
→
③ AWS 적용·확인
팀이 적용 시점을 정한 뒤 Terraform을 적용하고 Job과 앱의 RDS 연결을 확인합니다.

실제 RDS가 만들어지기 전에는 AWS 인증서로 연결되는지 확인할 수 없습니다. 코드는 apply 전에 작성·검토할 수 있고, 실제 RDS 연결 검증은 리소스가 준비된 뒤에 합니다.

연결 확인 시 Job 성공 및 앱 DB 연결 로그를 살펴봅니다. MariaDB 세션에서는 SHOW SESSION STATUS LIKE 'Ssl_version';로 현재 세션이 사용한 TLS 버전도 확인할 수 있습니다.

비용과 보안 경계

  • TLS parameter 설정이나 CA 번들 자체는 별도의 AWS 컴퓨팅 리소스를 만들지 않으므로 직접적인 신규 리소스 요금은 없습니다.
  • RDS, EKS, NAT Gateway 등 이미 설계된 AWS 리소스는 실제 생성 후 기존 사용료가 발생할 수 있습니다.
  • DB 비밀번호, AWS access key, 실제 금융 데이터는 예시 파일·ConfigMap·Git에 넣지 않습니다.
  • CA 번들은 공개 인증서 자료지만, 신뢰할 수 있는 AWS 공식 배포본을 사용하고 갱신 방법을 문서화합니다.
  • 이 문서는 코드 작업 지침입니다. AWS 인증, Terraform apply/destroy, 실제 리소스 생성은 수행하지 않았습니다.
