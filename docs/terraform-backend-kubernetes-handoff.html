SAI AWS Terraform 변경 및 앱·쿠버네티스 연동 전달서

담당: 한민엽(AWS·Terraform), 지인진(백엔드·Kubernetes) · 기준: sai-infra PR #10 · 2026-10-09

한눈에 보기
한민엽은 AWS·Terraform 기반을 만들고 리뷰 의견을 반영했습니다. 지인진은 백엔드와 Kubernetes를 함께 맡아 앱이 Redis·S3·DB와 Pod Identity를 실제로 사용하도록 연결하면 됩니다. 아직 AWS 리소스를 만들거나 terraform apply한 상태는 아닙니다.
이 문서의 범위
현재 PR의 코드와 후속 연동을 팀에 전달하기 위한 문서입니다. Terraform 코드 PR과 분리된 로컬 참고 문서이므로, 이 파일은 PR 변경에 포함하지 않습니다. 실제 AWS ID·주소·ARN이나 비밀번호·키는 적지 않았습니다.

1. 담당은 두 명입니다

담당해야 할 일완료 기준
한민엽
AWS·Terraform		두 AZ 네트워크와 NAT, Private EKS, Bastion/SSM, EKS 운영자 접근, Pod Identity 역할·연결, RDS/Redis/S3/ECR 및 IAM 정책을 관리합니다. Terraform 리뷰를 반영하고 팀에 output 규격을 전달합니다. 실제 Identity Center 역할에 정책/태그를 적용할 권한이 없다면 계정 관리자와 연결합니다.Terraform 변경과 팀 입력 규격을 준비합니다. AWS 계정 설정·비용 확인 전에는 apply하지 않습니다.
지인진
백엔드·Kubernetes		백엔드 Redis IAM 인증 + TLS 연결과 S3 prefix 설정을 구현합니다. Kubernetes에서는 앱 ServiceAccount/Pod Identity 사용, DB Secret·앱 설정 주입, AWS Load Balancer Controller·Ingress·Argo CD 배포, Private EKS 초기 접속 절차를 함께 맞춥니다.백엔드가 Terraform output으로 설정되고, 배포된 앱 Pod가 지정된 IAM 권한으로 Redis/S3/DB에 연결되며, Kubernetes 배포와 접속 절차가 문서화됩니다.

2. Terraform에서 바꾼 것과 이유

영역현재 코드왜 이렇게 했나
네트워크
modules/network		서울 리전의 AZ 2개에 Public/App Private/Data Private 서브넷을 만들고, AZ마다 NAT Gateway 1개씩 둡니다. App 서브넷은 자기 AZ의 NAT를 사용합니다. 자동 공인 IP는 꺼져 있습니다.한 AZ의 NAT에 양쪽 앱 트래픽이 몰리는 상황과 교차 AZ 의존성을 줄입니다. NAT 2개는 비용이 더 들지만, 이번 기본 설계는 AZ별 출구를 유지하기로 했습니다. NAT 2개만으로 서비스 무중단이 보장되지는 않습니다.
Private EKS + SSM
modules/eks		EKS API는 Private 전용입니다. Bastion도 App Private 서브넷에 있고 공인 IP/SSH 인바운드 없이 SSM Session Manager로 접근합니다. Bastion 보안 그룹에서 EKS API TCP 443만 허용합니다.인터넷에 SSH 포트를 열지 않고 팀원 IAM 역할의 세션 시작 권한을 사용합니다. 팀원 PC에서 여는 SSM 포트포워딩을 거쳐 Private API에 kubectl을 연결합니다. Bastion 인스턴스 역할에는 EKS 관리자 권한을 주지 않습니다.
운영자 권한
operator_access_entries		실제 팀원 IAM Role/User ARN을 명시 입력하고 EKS Access Entry와 정책에 연결합니다. 비어 있으면 검증에 실패합니다. 클러스터 생성자 자동 관리자 권한은 비활성화했습니다.누가 kubectl을 쓸지 명시적으로 관리하고, 생성자 개인 계정에 우연히 관리자 권한이 묶이는 것을 피합니다. 실제 역할 ARN과 필요한 최소 EKS 권한은 팀에서 채워야 합니다.
애드온 순서
modules/eks/main.tf		VPC CNI·kube-proxy·Pod Identity Agent는 노드 그룹 전에 만들고, CoreDNS는 노드 그룹 뒤에 만듭니다.CoreDNS는 실제 Worker Node에서 실행되어야 합니다. 노드가 CoreDNS를 기다리고 CoreDNS도 노드를 기다리는 의존성 대기/시간 초과를 피하기 위한 순서입니다.
Pod Identity
modules/iam		앱용 역할과 Pod Identity 연결을 Terraform에서 만듭니다. 기본 연결 이름은 Namespace sai, ServiceAccount sai-api입니다. Load Balancer Controller용 역할도 별도로 연결합니다.앱 Pod에 장기 AWS 키를 Kubernetes Secret으로 넣지 않고, Pod에 필요한 AWS 권한만 줍니다. 이 설계는 IRSA annotation 방식이 아닙니다.
워커 노드·로드밸런서
modules/eks, modules/network		초기 Worker Node는 AZ별 1대씩, 총 2대입니다. Public/App 서브넷과 노드 보안 그룹에 AWS Load Balancer Controller 탐색용 태그를 설정했습니다.Controller가 ALB를 만들 때 적절한 서브넷과 Pod ENI 보안 그룹을 찾도록 돕습니다. 2대 구성은 AZ 장애 무중단을 보장하지 않으며, HPA가 Pod 수를 늘리는 것과 노드 수를 늘리는 것은 별개의 조정입니다.
MariaDB
modules/data		RDS MariaDB 11.4 Multi-AZ, 비공개 접근, 저장 암호화, 자동 백업과 utf8mb4_unicode_ci를 설정했습니다. RDS master 암호는 Secrets Manager가 관리합니다.팀 로컬 DB 문자셋/정렬 규칙과 맞추고, 단일 DB 인스턴스 장애 영향을 줄이는 기본 구성을 택했습니다. RDS 자동 백업은 S3 앱 파일 버킷과 별개입니다.
Redis
modules/data		Redis OSS 7.1, 두 노드 Multi-AZ, 전송 TLS와 저장 암호화를 설정했습니다. 기본 사용자는 비활성화하고 앱 IAM 사용자는 auth:refresh:* 키 범위에 읽기/쓰기 권한을 받습니다.고정 비밀번호를 공유하지 않고 Pod Identity 역할로 IAM 인증을 쓰며, 앱이 필요한 키 범위만 접근하도록 합니다. 따라서 백엔드도 IAM 토큰을 발급·갱신하는 연결 구현이 필요합니다.
S3 파일 버킷
modules/storage, modules/iam		앱 업로드/내보내기 파일 버킷은 공개 접근 차단, HTTPS 전송 강제, SSE-S3(AES256), 버전 관리와 비현재 버전 수명주기를 설정합니다. 앱 권한은 exports/* 경로로 제한합니다.버킷 전체가 아닌 앱이 정한 prefix에만 권한을 줍니다. SSE-KMS를 쓰지 않으므로 앱 KMS 권한은 필요하지 않습니다. 이 버킷에 RDS 자동 백업이 자동 복사되는 것도 아닙니다.
로그
modules/eks		EKS 컨트롤 플레인과 대화형 SSM 셸 로그 그룹을 미리 만들고 보존 기간을 설정합니다.로그가 무기한 쌓여 비용이 커지는 것을 피하고 보존 기간을 명시합니다. SSM 포트포워딩 터널 안의 kubectl 요청 내용은 셸 로그에 기록되지 않으며, EKS audit 로그에서 별도로 확인해야 합니다.

3. 지인진이 할 일 — 백엔드 코드

Redis IAM 인증은 Terraform만으로 앱 연결까지 완료되지 않습니다. 현재 Terraform은 Redis 사용자/권한, TLS, Pod Identity 역할, IAM 정책과 output을 준비합니다. 백엔드가 IAM 인증 연결을 구현하기 전에는 실제 AWS Redis 로그인/세션 처리가 되지 않습니다.
  1. 고정 Redis 비밀번호를 사용하는 연결을 ElastiCache IAM 인증용 연결 설정으로 교체합니다.
  2. AWS SDK의 Pod Identity 자격 증명 체인을 사용해 IAM 인증 토큰을 만들고, Lettuce/Spring Data Redis 연결에 TLS와 토큰을 적용합니다. 토큰 만료 전에 재인증/연결 갱신이 되도록 합니다.
  3. Redis 요청 키가 실제로 허용 prefix auth:refresh:*에 속하는지 확인합니다. 다른 키가 필요하면 앱 코드와 Terraform 최소 권한 정책을 함께 조정합니다.
  4. 아래 Terraform output을 배포 설정에 연결합니다. 값은 AWS apply 이후에만 생성되며 지금은 실제 endpoint/ID가 없습니다.
  5. S3 저장 기능을 켤 때 file.storage=s3, file.s3.bucket, file.s3.key-prefix=exports/를 일치시킵니다. 저장한 객체 키가 exports/ 아래인지 확인합니다.
  6. 앱 DB용 최소 권한 DB 사용자를 만들고 자격 증명을 Terraform이 만든 앱 DB Secrets Manager secret에 안전하게 등록하는 절차를 DBA/백엔드와 정합니다. master 암호를 앱에 사용하지 않습니다.

4. 지인진이 할 일 — Kubernetes 설정·배포

  1. 앱 ServiceAccount를 정확히 맞춥니다. 기본값은 Namespace sai, ServiceAccount sai-api이며 Terraform Pod Identity association과 Deployment의 serviceAccountName이 같아야 합니다.
  2. IRSA annotation을 붙이지 않습니다. 이 인프라는 EKS Pod Identity 방식입니다. Terraform이 association과 IAM 역할을 생성하고, Kubernetes manifest는 동일한 ServiceAccount를 사용합니다.
  3. 앱 설정을 Secret/ConfigMap에 안전하게 주입합니다. Redis endpoint/ID, S3 bucket/prefix, DB Secret을 환경에 맞게 주입합니다. AWS 자격 증명 access key/secret key를 Kubernetes Secret이나 Git에 저장하지 않습니다.
  4. DB Secret 전달 경로를 정합니다. Terraform은 Secret 리소스와 앱 역할의 읽기 권한을 만들지만 Secret 값은 넣지 않습니다. Secrets Store CSI Driver/External Secrets 등 팀이 선택한 방법으로 주입하고, 실제 컨트롤러 설치 여부와 권한을 검증합니다.
  5. Load Balancer Controller의 ServiceAccount를 맞춥니다. 기본값은 kube-system/aws-load-balancer-controller입니다. Helm/manifest의 namespace와 ServiceAccount 이름을 일치시키고 Terraform Pod Identity 역할과 연결되게 합니다.
  6. Ingress와 ALB 동작을 검증합니다. Controller 설치 후 Ingress에서 요구하는 인터넷 공개 범위, target type, health check, 서브넷 선택을 확인합니다. Terraform은 Controller/Ingress YAML을 설치하지 않으며, 실제 ALB 생성과 2xx 헬스체크는 Kubernetes 배포 후 확인해야 합니다.
  7. Private EKS 초기 접속 절차를 문서화합니다. 팀원 PC의 AWS SSO + SSM 포트포워딩 + 로컬 kubectl 흐름을 안내합니다. Terraform은 EKS API 공개 접근을 열지 않았고, Bastion SSH 키 접속도 만들지 않았습니다.
  8. Argo CD·Metrics Server·앱 manifest는 Kubernetes 작업 범위로 둡니다. Terraform은 AWS 기반 IAM/네트워크와 관리형 EKS 기반만 다룹니다.

5. 한민엽이 확인할 일 — SSM 팀원 계정 매핑

Terraform 예시에는 operator_access_entries마다 EKS 접근 역할 ARN과 Bastion의 Linux 사용자명 run_as_user가 있습니다. Bastion 초기화 스크립트는 이 이름의 Linux 계정을 만듭니다. AWS SSM Session Manager가 실제 세션에 그 계정을 선택하려면, 팀원 IAM 역할에 SSMSessionRunAs 태그를 대응시켜야 합니다.

팀원 역할 태그: SSMSessionRunAs = 해당 operator_access_entries의 run_as_user 값
Terraform 예시 사용자명: sai-operator-1, sai-operator-2

한민엽이 AWS 계정에서 Identity Center 역할/권한 세트에 이 태그를 설정할 수 있는지 확인합니다. 직접 설정할 권한이 없으면 계정 관리자에게 요청합니다. 설정이 어렵거나 Identity Center 역할이 한 역할을 공유하는 방식이라면, 역할과 사용자 계정 설계를 먼저 맞춘 뒤 Terraform 입력을 조정해야 합니다. 서로 다른 팀원에게 같은 역할 ARN을 쓰면 개별 계정 식별이 되지 않을 수 있습니다.

팀원 역할에는 SSM 세션 시작 정책도 필요합니다. Terraform output bastion_operator_ssm_policy_arn이 Bastion 전용 SSM 접속 권한 정책을 제공합니다. 이 정책 부여와 실제 Identity Center 할당은 Terraform이 만들지 않습니다.

이 표는 팀 연동 규격입니다. 실제 AWS를 apply하지 않았으므로 리소스 ID·주소·ARN은 아직 생성되지 않았습니다.

8. 비용·보안·미완료 경계

  • NAT Gateway 2개, EKS 제어 플레인/노드, Bastion, RDS Multi-AZ, Redis 2노드, EKS Auth VPC Endpoint, CloudWatch 로그, S3/ECR 저장에는 비용이 듭니다. 작은 개발용 타입도 무료라고 볼 수 없습니다.
  • 초기 노드는 AZ별 1대이며 min/desired/max가 현재 1입니다. HPA는 Pod 수를 조정하고 Node autoscaler는 Worker Node 수를 조정합니다. 이 코드가 둘 모두 자동 확장하도록 만든 것은 아닙니다.
  • 실제 금융 데이터는 무료 외부 호스팅이나 외부 AI 서비스에 입력하지 않습니다. 실습/연동 테스트는 가짜 데이터로 합니다.
  • Terraform 출력은 팀 연동을 위한 값이지 자격 증명이 아닙니다. 암호·Access Key·실제 민감정보를 코드, 커밋된 tfvars, 이 문서에 넣지 않습니다.
  • 실제 AWS 계정 인증, plan/apply/destroy 및 리소스 생성은 이 문서 작성 범위에 포함되지 않습니다. 배포는 비용/계정/입력값 검토 후 팀에서 별도로 진행해야 합니다.
팀에 전달할 요약
“한민엽은 리뷰 의견을 반영해 AWS Terraform 기반을 정리했습니다. 지인진은 백엔드와 Kubernetes를 함께 맡아 Redis IAM 인증/TLS 연결, S3 exports prefix, sai/sai-api Pod Identity, DB Secret 전달, Load Balancer Controller/Ingress, Private EKS 초기 kubectl 접속 절차를 맞춰야 합니다. 현재 AWS 리소스는 아직 만들지 않았으며, 비용과 IAM 역할 입력을 확인한 뒤 별도로 배포를 결정합니다.”
