SAI EKS 요청서 및 Backend v2 연동 검토

sai-infra · sai-backend-v2 · sai-frontend · sai-mock-bank 대조 · 2026-10-09

내 인프라 제안: Worker Node 2대(t3.medium, AZ마다 1대), MariaDB RDS 11.4 + 서버 기본 문자셋 utf8mb4, Redis Multi-AZ 2노드를 유지합니다. 요청서의 t3.large 1대 대신 두 AZ에 노드를 나누는 선택입니다. 아래 연동 기준을 팀에 제안하고, 앱/쿠버네티스 담당 작업은 담당자와 나눕니다.

이 문서는 팀원의 EKS 요청서와 현재 작업 폴더의 앱·Terraform 코드를 대조하고 인프라 담당자의 권장안을 정리한 것입니다. 실제 AWS 리소스는 아직 생성되지 않았고, 아래의 앱·쿠버네티스 변경도 아직 수행하지 않았습니다.

내가 제안하는 연동 기준

  1. Redis: 현재 Terraform의 IAM 인증과 TLS를 유지하고, Backend v2에 AWS IAM 토큰을 발급하는 Lettuce 연결 설정을 추가합니다. 요청서의 고정 auth token 방식과 혼용하지 않습니다. Backend 담당자는 라이브러리·설정 변경 범위를 확인해 주세요.
  2. Pod 권한과 담당: 앱과 Load Balancer Controller 모두 EKS Pod Identity를 사용합니다. Terraform 담당(나)은 Pod Identity Agent add-on, sai/sai-api 및 kube-system/aws-load-balancer-controller IAM 역할과 association을 관리합니다. Kubernetes 담당자는 매니페스트/Helm 설정에서 같은 namespace와 ServiceAccount 이름을 사용합니다. ServiceAccount에 IAM 역할 annotation은 넣지 않습니다.
  3. 업로드 파일: 백업 export 버킷과 분리된 비공개 S3 파일 버킷을 만들고 SSE-KMS, 공개 차단, TLS 강제, 보존 정책을 적용합니다. Backend는 로컬 디스크 대신 S3 저장소 구현을 사용합니다. 앱 역할에는 필요한 prefix만 허용하며, 삭제 권한은 삭제 기능이 확인된 뒤 부여합니다.
  4. 배치: API Deployment 두 replica에서는 자정 스케줄러를 실행하지 않고, 단일 Batch Worker/CronJob으로 분리합니다. 재시도·중복 방지를 위해 작업을 멱등하게 하고 DB 기반 잠금을 둡니다. 실행 시간대는 Asia/Seoul로 명시합니다.
  5. 노드·HPA: 처음에는 AZ별 t3.medium 한 대씩으로 시작합니다. HPA 수치와 CPU/메모리 requests를 kind의 실제 계측값으로 정하고, 노드가 가득 찰 때만 Cluster Autoscaler 또는 Karpenter를 추가해 노드 상한과 비용을 제한합니다. 두 노드만으로 AZ 장애 무중단을 약속하지 않습니다.
  6. Mock Bank: Backend 서버 간 호출용 내부 URL과 브라우저 redirect용 HTTPS URL을 분리합니다. 사용자가 Mock Bank 화면을 열어야 하는 데모라면 HTTPS ALB/도메인을 별도 준비하고, DB와 내부 API는 공개하지 않습니다. 내부 API key는 Secrets Manager에서 각 앱이 읽게 합니다.
  7. 팀 출력: 요청서의 output 항목(cluster_name, region, API/Web ECR URL, RDS/Redis endpoint, 파일용 s3_bucket_name)을 맞춰 제공합니다. 기존 backup_bucket_name을 파일 업로드 버킷으로 오해하지 않도록 역할을 분리합니다.
  8. 버전·DB: MariaDB 11.4와 utf8mb4를 유지하고, 최초 DDL은 앱 replica와 분리한 1회성 작업으로 실행합니다. EKS는 배포 직전에 AWS 최신 지원 버전과 팀의 Controller/Argo 호환성을 확인합니다.

Terraform에 반영된 기본 인프라

  • EKS: API endpoint는 Private 전용. 운영 접속은 공인 IP/SSH 대신 SSM Session Manager를 사용하는 Private Bastion 경로입니다.
  • Worker Node: t3.medium 노드 그룹 2개, 각 App Private AZ에 한 대씩. 각 그룹은 min/desired/max가 1이라 노드 자동 확장은 아직 없습니다.
  • EKS 버전: 현재 기본값은 1.35입니다. 2026-10-09 기준 AWS는 1.37까지 표준 지원 중이므로, 실제 생성 시점에 최신 지원 버전과 Controller·Metrics Server·Argo CD 호환성을 함께 확인해야 합니다.
  • MariaDB: 코드에서 11.4와 mariadb11.4 파라미터 그룹을 사용하고 character_set_server=utf8mb4로 설정했습니다. RDS는 Multi-AZ, 비공개, 저장 암호화 및 자동 백업 설정입니다.
  • Redis: Multi-AZ 2노드, 전송/저장 암호화, IAM 인증 ACL 사용자. 앱 키 패턴 auth:refresh:*만 접근하도록 제한합니다.
  • 네트워크: 2 AZ의 Public/App Private/Data Private 서브넷, AZ별 NAT, Public 서브넷 ELB 태그, S3 Gateway Endpoint가 있습니다. EKS API는 인터넷에 공개되지 않습니다.
  • 스토리지: 현재 S3는 비공개 백업 export 버킷입니다. Public 접근 차단, TLS 강제, 버전 관리와 기본 SSE-S3(AES256)를 사용합니다. 이 버킷이 RDS 자동 백업이나 앱 파일 업로드에 자동 연결되지는 않습니다.

Backend v2 실제 코드와 AWS 설정의 중요한 차이

배포 기준: 검토의 주 대상은 요청서가 지정한 sai-backend-v2입니다. 참고로 구 sai-backend도 Redis Spring Data, 로컬 파일 저장, 자정 스케줄러 구조가 확인되어 배포 대상을 구 버전으로 바꾸면 아래 준비사항을 다시 확인해야 합니다.

영역Backend v2에서 확인한 동작최적 연동안 / 팀 조치
Redis Refresh TokenRefreshTokenService가 StringRedisTemplate으로 auth:refresh:{userId} 키에 SET/GET/DEL하고 TTL을 줍니다. ACL 키 패턴은 이 코드와 일치합니다. 다만 Gradle 의존성에는 AWS SDK가 없고 IAM 서명 토큰을 만드는 Lettuce credentials provider 설정도 확인되지 않았습니다.앱과 불일치
현재 IAM 인증 Redis는 앱이 그대로 연결할 수 없습니다. 권장안은 TLS를 유지하면서 Backend에 AWS IAM 인증용 Lettuce credentials provider와 AWS SDK를 추가하는 것입니다. 그 작업이 어렵다면 ACL password 사용자와 Secret 전달 방식을 정해야 합니다. 요청서의 단일 auth token 방식은 현재의 키별 ACL 사용자 구성과 차이가 있으므로 방식 하나를 선택해야 합니다.
서명·첨부 파일ArchiveService와 LoanContractFileService가 file.upload-dir 아래 로컬 파일시스템에 서명/첨부 파일을 저장하고 읽습니다. S3 SDK/client 코드는 없고, Terraform 앱 역할의 S3 권한은 exports/ 백업 prefix에만 있습니다.기능 미연결
두 Pod는 로컬 디스크를 공유하지 않으며 Pod 교체 시 파일이 사라질 수 있습니다. Backend에 S3 저장소 구현을 추가하고, 금융 문서용 private bucket/prefix를 별도 구성하는 안을 권장합니다. 전용 KMS 키 사용 여부와 다운로드/삭제 권한을 최소 범위로 정하세요. 현재 앱 코드에서 S3 삭제 기능은 확인되지 않아 DeleteObject 권한은 기본으로 열지 않습니다.
DB 스키마Backend SQL 파일은 utf8mb4 및 주로 utf8mb4_unicode_ci를 명시합니다. Docker Compose도 MariaDB 11.4를 사용해 새 RDS 버전과 맞습니다. 그러나 Flyway/Liquibase 의존성은 없고, 스키마 초기화 목록은 테스트 설정 중심입니다.운영 절차 필요
새 RDS는 테이블이 자동 생성된다고 가정하면 안 됩니다. 초기 DDL을 실행할 1회성 migration Job/절차를 정하고, 앱 DB 계정에는 최소 DML 권한만 주는 구성을 권장합니다. 두 앱 Pod가 동시에 스키마 초기화를 수행하게 두지 마세요.
정기 배치@EnableScheduling이 있고 자정에 실행하는 @Scheduled 메서드가 4개 있습니다. Pipeline은 매 실행마다 millisecond runId를 생성합니다. API Pod를 2개 띄우면 각 Pod가 스케줄을 실행해 같은 업무가 중복 수행될 수 있습니다.2 Pod 전 필수 조치
API Deployment에서는 스케줄러를 끄고 단일 Batch Worker/별도 Kubernetes CronJob으로 분리하거나, DB 기반 분산 잠금과 멱등 처리를 추가하세요. 자정 일정과 LocalDate.now()가 모두 Asia/Seoul 기준을 사용하도록 시간대를 명시해야 합니다.
Mock Bank 연결개발 설정은 Mock Bank 주소를 localhost:8081로 가리킵니다. EKS Pod 안의 localhost는 같은 Pod를 뜻합니다. Mock Bank Terraform 모듈은 별도 VPC용 선택 모듈이고 현재 root에서 호출되지 않습니다.배포 주소/네트워크 필요
EKS에서 접근 가능한 Kubernetes Service DNS 또는 별도 VPC 연결 주소로 sai.mock-bank.base-url을 설정해야 합니다. 실제 은행 데이터 대신 합성 데이터만 사용하고, 실데이터를 외부 무료 호스팅/외부 AI에 보내지 않는 경계를 유지하세요.
Mock Bank 브라우저 화면Backend v2는 Mock Bank의 /link/start로 사용자를 이동시키고, 동시에 서버 간 API에도 같은 base URL을 사용합니다. 별도 VPC 모듈은 EC2에 공인 IP를 지정하지만 인터넷 인바운드는 열지 않고, EKS App CIDR에서만 API 포트를 허용합니다. 모듈 README도 브라우저용 HTTPS/도메인 경로가 없다고 명시합니다.사용자 흐름 미완성
내부 API 주소와 브라우저가 접속할 Mock Bank URL을 앱 설정에서 분리하세요. Mock Bank 화면을 사용자가 브라우저에서 열어야 한다면 공개 진입점(예: HTTPS ALB/도메인/인증서)과 그에 맞는 인바운드 정책이 별도로 필요합니다. 선택 모듈의 현재 공인 IP만으로 화면에 접근되지는 않습니다. 테스트 범위/합성 데이터만 공개 경로에 두세요.
Mock Bank 내부 API 인증Backend는 X-Internal-Api-Key 헤더를 보내고 Mock Bank는 이를 검증합니다. 선택 모듈은 지정 Secret ARN만 읽지만, root에서 모듈을 호출하지 않으며 Backend Pod에도 동일한 비밀을 전달하는 연결은 없습니다.Secret 연결 필요
공유 API 키는 채팅·Terraform 변수 평문·이미지에 두지 말고, Backend와 Mock Bank가 각각 권한을 제한해 같은 Secrets Manager 값에 접근하도록 합의하세요. Secret rotation 절차와 내부 TLS/네트워크 경계도 배포 전에 정하세요.
런타임 설정·자격 증명Backend v2의 dev/prod profile YAML은 Git에서 무시되는 로컬 파일이며 공유 소스가 아닙니다. 현재 로컬 prod 설정은 Backend v2 서비스와 다른 Mock Bank 구성으로 보입니다. Dockerfile은 COPY src src를 하고 Docker ignore에는 profile YAML 제외 규칙이 없어, 로컬 Docker build에는 무시된 설정/credential이 이미지에 들어갈 수 있습니다.보안 우선 확인
로컬 profile 파일을 운영 이미지 설정으로 사용하지 마세요. 자격 증명을 환경변수/Secrets Manager와 Kubernetes Secret 주입으로 옮기고, Docker build context에서 local profile 파일을 제외하세요. 실제 유효한 credential이 이미지에 포함되었거나 공유됐다면 회전해야 합니다. 이 문서에는 비밀값을 넣지 않았습니다.
Pod IAM 연결Terraform은 앱과 Load Balancer Controller를 Pod Identity로 연결하며 EKS Pod Identity Agent add-on과 제한된 role trust를 설정합니다.팀 이름 일치 필요
Terraform은 sai/sai-api 및 kube-system/aws-load-balancer-controller association을 관리합니다. Kubernetes 담당자는 동일한 ServiceAccount를 매니페스트/Helm 설정에 사용하고 AWS role annotation을 추가하지 않습니다. Private 노드가 EKS Auth API에 접근하도록 EKS Auth Interface VPC Endpoint도 필요하며 시간·데이터 처리 비용이 발생합니다.
앱 IAM 범위RDS와 Redis 보안 그룹은 EKS worker node 보안 그룹 전체를 출발지로 허용하고, node/Bastion egress는 0.0.0.0/0입니다. 애플리케이션 IAM은 특정 ServiceAccount에 붙지만 네트워크 DB 접근은 같은 노드의 다른 Pod에도 열릴 수 있습니다.위협 모델 확인
데모에서 현재 구성을 수용할지, 서비스별 네트워크 정책/보안 그룹으로 좁힐지 팀 보안 담당자와 결정하세요. 금융 데이터 경계를 강하게 적용하려면 허용 egress 목적지, VPC endpoint, 로그/감사 보존도 함께 설계해야 합니다.
EBS CSI현재 Terraform EKS add-on에는 vpc-cni, coredns, kube-proxy, eks-pod-identity-agent가 있습니다. Backend 파일을 S3로 옮기면 파일 공유 목적의 EBS PVC는 필요하지 않습니다.사용 여부 확인
앱이나 Argo CD가 실제 EBS PersistentVolumeClaim을 쓰는 경우에만 EBS CSI Driver를 추가하세요. Pod Identity Agent와 EBS CSI는 서로 다른 목적입니다.
Frontend 이미지와 IngressFrontend는 Vite 앱이고 API 경로를 상대 경로 /api로 호출합니다. 현재 확인한 frontend 저장소에는 Dockerfile과 Kubernetes manifest가 없습니다. Terraform은 ECR 저장소를 만들지만 이미지 빌드/배포는 하지 않습니다.배포 산출물 필요
정적 파일용 웹 이미지/정적 호스팅 방식, SPA fallback, ALB 경로 라우팅(/api→Backend, 나머지→Frontend)을 쿠버네티스 팀과 정하세요. 요청서의 overlays/demo가 현재 작업 폴더에 없으므로 별도 산출물 확인이 필요합니다.

노드 2대 결정과 쿠버네티스 배치

요청서의 t3.large 1대 대신 t3.medium 2대를 유지하기로 했습니다. 두 노드는 AZ 두 곳에 분산되어 한 노드가 실패해도 다른 노드가 남을 여지를 주지만, AZ 전체 장애 때 무중단을 보장하지는 않습니다. 또한 각 노드의 CPU/메모리는 t3.large 1대보다 작으므로 20여 Pod라는 개수만으로 용량이 충분하다고 판단할 수 없습니다. 팀이 kind에서 잰 CPU·메모리 request/limit과 실제 배포 결과를 AWS에서도 확인해야 합니다.

요청서 추산은 앱 Pod 4개와 시스템/Argo/Controller Pod를 합해 약 20개입니다. t3.medium의 노드별 Pod 한도와 DaemonSet 자리도 각 노드에서 따로 적용됩니다. HPA는 Pod 수만 늘리고 현재 Terraform의 min/desired/max=1인 AZ별 node group은 노드를 늘릴 수 없습니다. 데모는 2대로 고정할지, Cluster Autoscaler/Karpenter와 함께 AZ별 max를 늘릴지, HPA max를 어디까지 둘지 합의하세요. 롤링 배포 중 추가 용량이 필요한지와 PodDisruptionBudget/분산 규칙도 Kubernetes 팀이 확인해야 합니다.

팀과 맞출 순서

  1. Backend 담당자: Redis IAM+TLS 연결 가능 여부, S3 저장소 구현 범위, 스케줄러를 Batch Worker로 분리하는 방법, DB 초기 DDL 절차, Mock Bank URL 분리와 callback을 검토.
  2. Kubernetes 담당자: Terraform이 관리하는 Pod Identity association과 앱 sai/sai-api/Controller kube-system/aws-load-balancer-controller ServiceAccount 이름을 맞춥니다. Pod Identity Agent는 Terraform EKS add-on으로 설치됩니다. EBS CSI 필요 여부, API·Web replica와 HPA 목표, 노드 autoscaler, Frontend 이미지·/api 라우팅·ALB health check도 확인합니다.
  3. 함께 결정: Mock Bank 내부 API 주소와 브라우저 URL을 분리하고, `/link/start`를 위한 HTTPS 진입점, 내부 API key Secret 연결, Backend callback 주소를 합의.
  4. 배포 산출물: Frontend Dockerfile/정적 호스팅, `/api` 경로 라우팅, Ingress/ALB health check, 도메인·HTTPS 적용 시점을 Kubernetes 담당자가 준비.
  5. 계정·보안: 운영 Secret 주입, 합성 데이터만 허용, 접근 egress 범위, node SG를 통한 DB/Redis 접근 허용 범위와 감사 로그 보존을 검토.
  6. 값 전달 계약: 요청서 output 이름을 alias로 제공하고, s3_bucket_name은 새 파일용 버킷을 가리키게 함. DB host와 Secret ARN만 공유하고 암호는 전달하지 않음.
  7. 실행 준비: 서울 리전의 최신 지원 EKS 버전을 우선 검토하고, 팀 애드온 호환성이 없으면 검증된 버전을 고정하며, 원격 tfstate/lock·비용·파일 추적 상태를 합의한 다음 별도 승인 뒤 apply.
  8. 공동 Terraform 실행 전: 원격 tfstate와 state lock을 설정하고 output 이름 계약을 확정. 현재 sai-infra 상태에서는 Terraform 소스 파일이 아직 Git 추적되지 않은 것으로 보여, 팀 공유 전에 추적/커밋 여부도 확인.
  9. 그 후: 코드 검토와 비용 확인을 마치고 별도 승인을 받은 뒤 AWS apply. 앱/Ingress 정리 후에만 destroy.

공유 전 보안 조치: 실제로 할 일

전달물 구분: 이 HTML에는 credential 값과 외부 서비스 주소를 넣지 않았으므로 HTML 자체는 팀에 공유할 수 있습니다. 아래 조치는 HTML을 보내기 위한 포맷 작업이 아니라, Backend 설정·Docker 이미지·Git·AWS Secret을 안전하게 운영하기 위한 후속 작업입니다. profile 파일이나 그 화면 캡처는 HTML과 함께 보내지 마세요.

발견된 상황: Backend v2의 로컬 전용 application-dev.yml/application-prod.yml은 Git에서 무시되지만, 로컬 Dockerfile은 COPY src src로 소스 전체를 빌드 단계에 복사하고 Backend v2에는 이 파일을 제외하는 .dockerignore가 없습니다. 따라서 그 PC에서 이미지를 빌드하면 Git에 커밋되지 않은 profile 설정도 빌드 context/JAR에 들어갈 수 있습니다. 파일 안의 값이나 외부 DB 주소는 이 문서에 옮기지 않았습니다.
  1. 로컬 파일을 안전하게 점검: Backend 담당자가 로컬 profile 두 파일을 열어 DB 계정, API 키, JWT/서명 키 등 실제 비밀값이 있는지 확인합니다. 파일 내용을 채팅·이슈·HTML에 붙이지 말고, 값이 진짜인지와 어느 시스템 자격 증명인지만 분류합니다. git status에 안 보인다는 사실만으로 Docker 이미지에서도 안전하다고 판단하지 않습니다.
  2. Docker 빌드에서 제외: Backend v2에 .dockerignore를 추가해 src/main/resources/application-dev.yml, src/main/resources/application-prod.yml 및 로컬 비밀 설정 파일을 제외합니다. 빌드 context와 최종 JAR에 해당 값이 없는지 확인하고, CI는 저장소에 없는 로컬 profile이 아니라 승인된 Secret 주입을 사용하게 합니다.
  3. 이미 노출된 값은 회전: 값이 실제 유효하거나 이미지/공개 Git/로그/채팅에 올라간 적이 있으면 원래 값을 단순 삭제하는 데 그치지 말고 해당 DB·API 제공자에서 폐기/재발급합니다. DB 암호, 내부 API key, JWT/서명·해시용 비밀키, 외부 연동 자격 증명을 각각 교체하고 새 값은 공유하지 않습니다. 공개 저장소의 Git 이력에 올라간 적이 있으면 노출된 것으로 간주합니다.
  4. 운영 Secret 전달 경로 정하기: 값은 AWS Secrets Manager를 원본 저장소로 두고, Pod에는 Pod Identity와 Secrets Store CSI/External Secrets 등 팀이 선택한 연동으로 런타임에 전달합니다. Terraform에는 secret 값 대신 ARN/리소스 참조만 둡니다. master DB 암호와 앱 DB 계정을 분리하고, 앱 DB 계정에는 필요한 데이터베이스 권한만 줍니다.
  5. Mock Bank Secret도 분리: Backend의 link-callback.api-key와 Mock Bank의 검증 설정은 같은 비밀값을 안전하게 참조하게 하되 서로 다른 IAM 역할에는 해당 Secret만 읽도록 제한합니다. user-data, Terraform state, 이미지, Compose 파일, 로그에 secret 본문이 출력되지 않는지 확인하고 교체 절차를 정합니다.
  6. 실데이터 경계 지키기: 로컬 profile에 설정된 외부 호스팅 DB는 합성 데이터 테스트만 허용합니다. 실제 금융 데이터·개인정보를 외부 무료 DB, 공개 저장소, 외부 AI 서비스에 넣지 않습니다. 잘못 전송된 이력이 있으면 연결을 끊고 자격 증명을 회전한 뒤 팀 보안 담당자에게 알립니다.
  7. 공유본과 Git 확인: 팀에 전달할 HTML/스크린샷/로그에 계정·주소·비밀값이 없는지 확인합니다. 현재 sai-infra Terraform 파일은 Git 미추적 상태이므로 의도한 파일만 추가하고, .tfstate, 실제 .tfvars, profile 파일, .env, 빌드 이미지/로그는 커밋하지 않습니다. 이미 커밋한 비밀은 파일을 지우는 것만으로 해결되지 않으므로 먼저 회전합니다.

완료 기준: Docker 빌드 입력에서 로컬 비밀 profile이 빠짐, 유효/노출 자격 증명 회전 여부 확인, 새 Secret을 저장·주입할 담당과 권한 확정, 공유 자료에 비밀값이 없음. 이번 HTML 수정에서는 profile 값이나 외부 서비스 주소를 기록하지 않았습니다.
